# GCP Smart Home Hub — Cloud Run / Cloud SQL

This is the GCP port of the AWS-based platform under `aws/`. The
terraform here is now valid against the GCP provider and `terraform
apply` deploys a working Cloud Run + Cloud SQL + Artifact Registry
stack — but the service containers themselves still call AWS SDKs
(boto3) at runtime, so they will boot but fail on any operation that
touches SQS / Secrets Manager / etc.

## What this folder deploys today

| Concern | AWS | GCP (this folder) |
|---|---|---|
| Compute | ECS Fargate behind ALB | Cloud Run v2, per-service `*.run.app` URLs |
| Container images | ECR + `docker push` | Artifact Registry + `docker push` (`modules/registry`) |
| Database | RDS Postgres in private subnets | Cloud SQL Postgres, reached via the Cloud SQL Auth Proxy |
| Service identity | One ECS task role + scoped tuya-bridge role | One `google_service_account` per service |
| Inbound auth | API Gateway in front of ALB | Direct invocation; `roles/run.invoker` for `allUsers` |

No VPC / networking module — Cloud Run is fully managed and reaches
Cloud SQL through the Auth Proxy's unix socket, so a Serverless VPC
Connector isn't needed for this topology.

## What's intentionally NOT here yet

These all stay AWS-shaped in the service code; they'll move when the
SDK abstraction lands in a follow-up PR.

- **Event bus.** `analytics-service` still tries to `boto3.client("sqs")`.
  Pub/Sub replacement comes with the abstraction layer.
- **Secrets.** `JWT_SECRET` and `INTERNAL_TOKEN` are passed as plain Cloud
  Run env vars (still generated by `random_password`). The AWS side moved
  these into Secrets Manager via the task definition's `secrets` block —
  the GCP equivalent (Secret Manager + Cloud Run secret env) lands with
  the abstraction.
- **Tuya Cloud creds.** `tuya-bridge` still reads `boto3.client("secretsmanager")`.
  `tuya_client_id` / `tuya_client_secret` aren't even wired through
  `variables.tf` yet — only the device-ID allowlist is.
- **Cross-service URLs.** `TUYA_BRIDGE_URL` and `DEVICE_SERVICE_URL`
  point at the AWS ALB DNS today. The Cloud Run URLs form a cycle
  (`device-service` ↔ `tuya-bridge` both need each other), and the
  service code uses boto3 anyway, so plumbing them is deferred.

`push_images.sh`, `redeploy.sh`, `set_tuya_secrets.sh`, and `test_apis.sh`
are still the AWS scripts — they're left as-is for the SDK-abstraction PR
to swap in GCP equivalents.

## Cost note

The default `min_instances = 2` keeps two warm containers per service —
five services × two containers × 1 vCPU = ten always-allocated vCPUs.
That's well above the Cloud Run free tier (~240k vCPU-seconds/month),
so a stack left running for a week is not free. Set `min_instances =
0` in `terraform.tfvars` if you don't need the load-balancer demo, and
`terraform destroy` between demos.

## Running it

```bash
cd gcp/terraform
cp terraform.tfvars.example terraform.tfvars
# Fill in gcp_project_id and db_password at minimum.

gcloud auth application-default login
gcloud config set project <your-project-id>

terraform init
terraform apply
```

The build-and-push step needs `docker` + `gcloud` on the machine running
apply (same shape as the AWS module needing `docker` + `aws`).

After apply, `terraform output service_urls` returns the five public
service URLs. Each service is reached directly at its own `*.run.app`
hostname — there is no shared API Gateway in this deployment.
